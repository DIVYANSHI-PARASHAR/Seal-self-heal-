# Automatic evolution from a failed question

## Goal

When an operator question produces a verified capability gap or harness bug, start an evolution job automatically. While the model diagnoses the failure, show the actual harness as a workflow diagram: agents, tools grouped under their owning agents, connected databases/data sources, external systems and runtime MCP servers, and context sources. Ground the diagnosis in recorded evidence and show a proposed change in its place in that diagram. A missing-tool proposal appears under the relevant agent's Tools group before it is implemented.

Once the proposed change has become a screened candidate commit, automatically evaluate the previous and updated harness against the same frozen evaluation plan. Plot the previous version's results and build the candidate's results live as trials finish. If the candidate passes the protected selection gates and its exact commit is activated, run the original question again on that version and show the new run. If it cannot be fixed safely, keep the incident and reason visible without presenting a successful repair.

The workflow is a persisted, versioned artifact that can be opened at any time, including outside an evolution job. Update it with each harness revision while retaining previous diagrams, proposals, and evaluation evidence. The question stays in the top bar on the Evolve, Harness, Runs, Evaluations, Versions, and final answer pages. The original run, evolution job, workflow revisions, candidate, evaluation plan, activated version, and rerun have stable links to one another.

## Implementation status

- `POST /api/runs` captures the source-derived workflow before execution, records the run, and creates one durable evolution job for each eligible incident. The response includes a stable Evolve URL; refreshes and worker restarts replay persisted job events rather than depending on the browser.
- The web worker dispatches by the persisted task-family contract: the protected inventory controller handles Atlas questions and the protected logistics controller handles shipment-threshold gaps. The logistics path freezes the observed bundle, an independent generated bundle, private variations, a refusal case, and inventory regressions before it runs the same paired selection and promotion gates. Both controllers emit ordered progress records from diagnosis through proposal, frozen evaluation, selection, promotion, and the pinned post-activation rerun.
- `harness_workflows` retains immutable, deduplicated inventory and logistics diagrams. Runs, candidates, trial records, versions, and active-version compare-and-swap records bind to those revisions. The Harness page can open a saved graph or its verified diff without executing harness code.
- The logistics candidate runner and isolated container bridge accept only a typed bundle with `inspect_catalog`, `inspect_relation`, and bounded `read_shipments`. It imports the candidate's pinned logistics agent and registration, verifies observed tool execution and the terminal signed shipment scan, and powers active logistics versions in the browser and the activation rerun path.
- The current reviewed logistics v2 tool already answers the threshold question. A genuine end-to-end missing-tool demonstration therefore still requires an explicitly pinned historical v1 source or a new unsupported logistics contract; the product never silently downgrades the active version or rebrands the reviewed v2 tool as a generated repair.
- Model proposals remain a single recorded JSON proposal. The UI shows actual run, tool, candidate, and evaluation evidence; it does not invent a reasoning transcript or model tool calls.
- Atlas and LangSmith development MCP connections are inspection tools for developers, not harness runtime dependencies (see [development connections](development-connections.md)). Diagrams show an MCP only when the harness configures it or a proposal clearly labels it `needs_contract`.

## Intended operator experience

The Evolve page has a stage strip, a large workflow canvas, an evidence inspector beside it, and a live evaluation comparison below it. Keep the canvas mounted throughout diagnosis, proposal, evaluation, and activation so changes retain their visual location. The default view follows the current job stage; selecting a historical revision or inspecting evidence pauses automatic view switching without stopping the job.

| Stage | Workflow view | Evidence and results |
| --- | --- | --- |
| Diagnosing | Show the saved incident harness immediately; highlight components implicated by available evidence. | Actual diagnostic steps, observed failure, and concise evidence-backed hypothesis; show uncertainty until diagnosis is supported. |
| Change proposed | Add a dashed, labeled proposed node under the owning agent's Tools group, with proposed dependency edges. Show modifications/removals similarly. | What is missing, why the change could fix it, affected components, required access, and proposal/diff references. |
| Candidate ready | Replace the proposal preview with the graph derived from the exact screened candidate commit; retain a Before / Proposed / Candidate comparison. | Which proposed changes were implemented, screening outcome, commit, and frozen evaluation plan. |
| Evaluating | Show the candidate diagram with trial activity overlaid only where recorded. | Baseline results and progressively completed candidate plots, paired trial rows, progress counts, and required gates. |
| Activated or stopped | Show the activated diagram, or preserve the rejected/blocked candidate with its status. | Promotion decision, unresolved reason, original-versus-rerun outcome, and links to all workflow revisions. |

Example: on a pinned logistics v1 failure, the relevant agent's Tools group gains a proposed `count_customers_over_shipment_threshold` node, connected to the approved logistics session and shipment source. This does not indicate that the tool is already executable. After screening and commit creation, the candidate graph shows its actual registration and dependencies; only recorded evaluations and promotion can make it the active harness.

## Implementation sequence

### 1. Detect an eligible incident and create one durable job

Add a trusted incident classifier after the run record is complete. Auto-start only for `unsupported` with `limitation_kind=capability_gap`, a deterministic harness error with a supported contract, or an independently verified wrong answer. Network, Atlas, model-provider, and trace outages are operational failures, not patch requests. An answered run with no oracle check is not automatically called a bug.

Persist an `evolution_jobs` record in Atlas keyed by the incident run ID (unique index) before returning the run response. Save the original question, input kind, dataset ID and content hash, task family, observed commit, incident workflow revision ID, current stage, timestamps, and links to cases/candidates/selection. Use a conditional claim or lease so double clicks, retries, concurrent requests, and server restarts cannot start duplicate jobs. Return `evolution_job_id` and `evolution_url` with the original run.

### 2. Run evolution outside the HTTP request

Move controller invocation into a supervised background worker. The request returns as soon as the incident and job are recorded. The worker resumes or marks interrupted jobs on startup; it does not depend on a browser tab remaining open. Add bounded retries only for transient infrastructure failures, respecting existing patch-attempt limits. Record terminal states such as `activated`, `rejected`, `needs_contract`, `blocked`, and `operational_error` with concrete reasons.

Emit persisted stage events from the real controller boundaries: incident classified, workflow snapshot ready, trace read, original case frozen, generated case frozen, baseline reproduced, proposal received, diff screened, candidate commit and workflow created, evaluation plan frozen, each baseline/candidate trial started/completed, selection decided, and promotion completed. Include candidate/attempt identity and workflow revision IDs so retries do not mix diagrams or results. Persist the underlying record before publishing its event; use stable event IDs and monotonically increasing per-job sequence numbers for replay and deduplication. Store IDs, timings, commits, and redacted evidence references, not raw private rows, oracle answers, credentials, or private case content. The UI consumes these records through `GET /api/evolution-jobs/{id}` and `GET /api/evolution-jobs/{id}/events`; polling is enough initially, with SSE optional later. The job snapshot includes its event cursor so reconnect can reconcile without missing updates.

### 3. Persist the harness workflow and derive trustworthy revisions

**Graph contents and provenance.** Define a small typed graph rather than a screenshot or model-generated illustration. Each node has a stable logical component ID, kind, display label, owning agent/group where applicable, safe configuration/schema summary, content fingerprint, and provenance references. Represent agents; tools nested under agents; context sources such as instructions, task input, and bounded tool-result history; trusted data adapters; databases/data sources; model providers; and actual external integrations/MCP servers. Represent shared services once and connect each user to them. Give edges explicit types such as `invokes`, `reads_via`, `supplies_context`, and `calls_external`. Keep structural connections distinct from observed execution order and repeated calls.

Derive the graph from pinned source and the run's effective configuration using explicit trusted adapters for supported harnesses. Obtain candidate registration metadata only through bounded inspection in the existing isolated runner; never import candidate code into the web server. Validate metadata against the screened source and approved bridge capabilities. Source/configuration establishes available components; trace evidence establishes which were actually used. Unresolved dynamic dependencies are labeled unknown, not inferred as working connections. Model-produced diagnosis and proposed edges remain annotations until verified against the candidate. Changes to context instructions, schemas, or limits must be visible even when node names stay the same.

Keep the editable harness boundary and trusted host boundary visible. Tools connect to Atlas through the scoped data interface. Evaluation oracles, the evolution model, storage, and tracing can appear in a collapsed supervisor group; they must not look like callable analyst tools. Show only configured context sources and integrations, with absent categories omitted or marked empty. A proposed new MCP, database, or permission outside the approved runtime contract remains `needs_contract`; drawing it does not grant access or expand the automatic patch boundary.

**Durable revision model.** Store immutable `harness_workflows` snapshots in Atlas with `workflow_revision_id`, task family, source commit, configuration/environment fingerprints, graph schema and extractor versions, graph content hash, nodes/edges, creation time, and provenance. Use a unique identity over task family, commit, effective configuration/environment, schema version, and extractor version. Exclude secrets, case inputs, and display-only node positions from that identity. Deduplicate captures of the same identity; a different graph hash for that identity is an integrity error to resolve, not an overwrite. Keep dataset hashes and actual access evidence on run/trial bindings, avoiding separate topology copies for every evaluation dataset.

Capture a baseline snapshot when a version is first used and bind each new run to its revision before execution. An evolution job opens that saved incident revision while diagnosis is running. Backfill older versions only from their pinned commit and recorded configuration; if either is unavailable, display an explicit incomplete-history state rather than substituting today's harness. Snapshot failure does not erase the recorded incident: retain a blocked stage and retry capture before proceeding with evolution.

Persist proposed graph changes separately on the candidate proposal, referencing a base revision, owning component IDs, evidence, and proposed additions/modifications/removals. A proposal is not an executable version. After screening, derive and save the actual candidate snapshot and compute a structural diff against its parent using stable component IDs. Record the parent/child link on candidate/version lineage records so identical snapshots can be reused without rewriting ancestry. Compare the proposal to the actual diff; unexpected or unresolved changes must be visible and resolved before activation. Preserve rejected proposals and candidate snapshots too.

Promotion atomically updates the active commit and `workflow_revision_id` in the same compare-and-swap record after the candidate snapshot exists and matches the tested identity. Rollback restores both together. Lifecycle status comes from job/candidate/version records rather than mutating historical graph content. In-flight runs and historical links keep their original revision. Schema/extractor upgrades create new snapshots with explicit lineage; they do not rewrite diagrams bound to previous runs.

**Always-available workflow view.** Add a Harness sidebar entry at `#harness`, with task-family selection, the active workflow, retained version history, and a stable `#harness/{workflow_revision_id}` link. Link it from Evolve, Runs, Evaluations, and Versions. Support Before / After and overlay diff views, plus a component inspector for registration/schema, context summary, dependencies, source references, and linked evidence. Deterministic layout and stable IDs keep unchanged nodes in place across revisions. Save optional layout preferences separately from graph truth. Diagram structure and history must remain available after refresh, server restart, worker exit, or loss of external trace access; explain when linked evidence is unavailable.

### 4. Make logistics a real candidate path

Extend the candidate runner and container RPC to accept a typed logistics bundle. Expose only the approved `inspect_catalog`, `inspect_relation`, and bounded `read_shipments` operations; preserve dataset scoping, frozen time semantics, cursor validation, page/byte/time budgets, and no Atlas credentials in the container. Dispatch the candidate's logistics agent/tool registration from its pinned `harness/` commit, rather than always importing the server's built-in `LogisticsAgent`.

Add logistics-specific scenario generation, a frozen original case, an independent oracle, generated reproduction, private variations, negative refusals, and inventory regressions to the controller/evaluator. The comparison must run the same frozen cases and limits against the old commit and proposed commit. A proposed `count_customers_over_shipment_threshold` tool must be a screened harness-only diff and a tested candidate commit. A passing standalone logistics tool check is insufficient for promotion.

### 5. Start evaluations automatically, plot live comparisons, and activate exact tested code

Automatically start protected selection after the diff passes screening, the candidate commit and validated workflow snapshot are saved, and the evaluation plan is frozen. Key this transition by candidate ID and plan ID so reconnects or worker retries resume it without queuing a second evaluation. The browser observes this process; opening the chart does not trigger trials.

Keep the existing patch scope, Docker isolation, immutable evaluation plan, repeat trials, resource ceilings, trace requirements, and `PromotionManager` compare-and-swap. Bind the plan to the baseline and candidate workflow revisions as well as their commits and configuration/environment identity. Compute a transparent scorecard from stored trial records: original incident, newly generated case, existing regressions, private validations, negative refusals, resource/cost checks, and overall decision. Show baseline and candidate side by side for each case, with failures and skipped trials visible. Do not reduce selection to a single percentage that hides required gates.

Use paired baseline/candidate plots with a fixed case-group order: original incident, new reproduction, regressions, private validation, and negative refusals. Display passed/failed/completed counts against each group's fixed scheduled total, plus a separate required-gates summary. Populate baseline results as they are recorded, then fill the candidate series as trials finish; retained baseline points stay visible throughout candidate evaluation. Execution may be interleaved, so either series can initially be pending. Incomplete, running, skipped, blocked, and infrastructure-error trials have distinct states and never become fabricated zero scores. Mark the comparison provisional until required trials finish. The frozen denominator does not shrink when cases fail or are skipped.

Below the correctness chart, offer separate latency, tokens, and data-read plots with units and sample counts. Show cost only when recorded usage and pricing support it. Compute deltas only over completed matched case/repetition pairs with the same dataset hashes and limits; aggregate using the existing evaluator's scoring rules. Keep earlier runs and incident-reproduction checks labeled as historical context unless they meet the full plan identity. Initially rerun both versions within the same plan rather than adding a baseline-result cache.

The detailed matrix is the source of truth behind the charts: case role and public label or opaque protected label, repetition, baseline/candidate status, run IDs, measured resources, safe pass/fail reason, and trace links. Selecting a point opens its row and linked run and can highlight observed components on the corresponding workflow revision. Protected validations expose only permitted aggregate/status metadata, never private inputs, oracle answers, raw tool arguments, or detailed failure text that reveals them. Rebuild charts from persisted trials after refresh; deduplicate updates by plan, side, case, and repetition, retaining explicit retry-attempt lineage. Keep candidate attempts separate with a selector rather than blending their results.

The active-version record changes only after all required gates pass for the exact candidate commit, workflow revision, and environment identity. In-flight runs stay pinned to their starting version. If the parent version changes during evaluation, mark the candidate stale and create a new linked candidate/plan against the new parent; do not mutate the frozen comparison or overwrite the active version. Keep the previous code and workflow revision available for rollback.

### 6. Add the Evolve page and automatic navigation

Add `#evolve/{job_id}` and an Evolve item in the sidebar. On an eligible run response, navigate there immediately and keep the original question in the shared top bar. On reload, use the job ID in the URL to restore progress. The page should show:

1. Original outcome, version, Atlas record, LangSmith trace, and the exact ordered analyst tool calls (including `0 calls` where true).
2. The persisted incident workflow during diagnosis, with agents and their Tools groups, data/context dependencies, and configured external systems. Show a concise diagnosis summary and evidence links, the frozen original/new case IDs, and the baseline reproduction result. Do not present hidden model reasoning or guessed intermediate steps as a live transcript.
3. The proposed change at its location in the graph, then the actual candidate workflow and structural diff. Include proposal hypothesis, proposed tool name, required dependencies, screened code diff, changed files, candidate commit, and status. The code panel reflects the saved diff; it never animates a fictional edit.
4. Live baseline-versus-candidate charts above the evaluation matrix described in step 5. Keep previous-version results visible as the updated harness's results arrive. Highlight observed trial activity on the matching diagram only when event evidence supports it; an unobserved tool remains available but unused.
5. Activation result, active/previous commit and workflow links, and a linked rerun. Rejected or blocked jobs remain on this page with the actual failure reason and no auto-rerun claim. The saved workflow is also accessible through Harness after leaving Evolve.

Keep the question input visible on every page, as in the supplied reference UI. Distinguish original run tool calls, proposed tool definition, evaluation tool calls, and final rerun tool calls with explicit labels.

Use labels and icons as well as color for proposed, changed, removed, active, and failed states. Provide keyboard-accessible component navigation, an equivalent structured list/table, fit-to-view and zoom, and reduced-motion behavior. On narrow screens, stack the inspector below the canvas. Updates must not reset focus, selection, or scroll. Show last-update/reconnecting status while preserving the last confirmed graph and results.

### 7. Rerun after activation and return to Ask

When the job reaches `activated`, the server starts exactly one rerun using the original question, original immutable dataset, and the exact activated commit and workflow revision recorded on that job, even if another version becomes active later. Record `rerun_run_id` and link it to the incident/job. If that run answers successfully, the UI navigates to `#ask` with the completed answer and evidence visible, including the new tool call and saved workflow link. Only auto-navigate while the user is still following that job; otherwise show a completion link without interrupting their work. If it fails, keep the Evolve page open with the failed rerun and avoid a success banner. The rerun trigger is idempotent and survives refresh or reconnect; do not recursively auto-evolve that rerun as a new incident without the existing job's bounded retry policy.

## Proposed API and record changes

- `POST /api/runs`: unchanged question input; response gains `evolution_job_id`, `evolution_url`, and `evolution_state` only when an incident was queued.
- `GET /api/evolution-jobs/{id}`: summary, question, stage, event cursor, linked run/candidate/plan/version/rerun IDs, baseline/proposed/candidate/activated workflow references, scorecard, and safe display data.
- `GET /api/evolution-jobs/{id}/events?after={sequence}`: ordered, paginated persisted progress with stable event IDs and a next cursor.
- `GET /api/harness-workflows?task_family={family}`: active revision reference and paginated retained revision history, including candidate/version lineage and current lifecycle labels.
- `GET /api/harness-workflows/{revision_id}`: saved typed graph, identity, provenance, and links; render it without rerunning the harness or requiring LangSmith access.
- `GET /api/harness-workflows/{revision_id}/diff?base={base_revision_id}`: verified additions, removals, configuration changes, and edge changes between compatible revisions. Proposal overlays come from saved candidate records and are explicitly labeled.
- `GET /api/evolution-jobs/{id}/evaluations?plan_id={plan_id}&cursor={cursor}`: paginated redacted paired trial records and server-derived chart/gate summaries, with plan identity and a snapshot watermark for consistent refresh.
- `GET /api/runs/{id}`: include linked workflow revision and evolution job and, for the final run, its originating incident. Extend existing evaluation/version responses with workflow revision links too.
- Atlas: `evolution_jobs` with unique incident ID, stage/event sequence, lease ownership/expiry, bounded attempts, workflow references, and rerun ID; `harness_workflows` with immutable graph snapshots and a unique identity index. Store compact, bounded stage events with job/sequence uniqueness; keep detailed model/tool traces in LangSmith. Add proposal graph annotations and revision references to existing candidates, selection plans, evaluations/runs, and versions. Extend `active_versions` so commit and workflow reference change atomically. Reuse existing trial records as chart truth, not a second evaluation store.

## Additional product refinements

- **Explain the proposed fix.** The component inspector answers what failed, what is changing, which dependencies it needs, and which evaluation will demonstrate the repair. Treat suspected cause, reproduced failure, and validated repair as separate claims.
- **Show regressions as prominently as gains.** Surface a worsened case or resource gate beside the improvement, with links to the paired evidence. Passing the original question alone is never the completion signal.
- **Make history useful.** Open any retained workflow directly, compare it with its parent or the active version, and show the job and evaluation decision behind each change. Preserve rejected attempts as inspectable history without presenting them as active capabilities.
- **Keep the first implementation focused.** Use the existing UI stack, deterministic layouts, and polling. Build an inspectable workflow viewer and version diff; a drag-and-drop harness editor, arbitrary integration provisioning, streaming model reasoning, and a new orchestration framework are not prerequisites.

3. The job creates immutable original/new cases, reproduces the baseline failure, and persists the missing-tool proposal under the correct agent with dependency edges and evidence. Refresh before implementation restores that proposal without presenting it as an executable tool.
4. Screening and commit creation produce a verified candidate workflow diff and automatically start one frozen selection plan. The Evolve page shows real model/proposal steps, safe tool evidence, the diff, four or more logistics variations, inventory regressions, and the promotion decision.
5. Baseline plots remain visible while candidate results arrive one recorded trial at a time. Fixed denominators, repetitions, provisional states, resource units, failures, skips, and required gates are accurate. Refresh, replayed/out-of-order events, and multiple candidate attempts do not duplicate points or mix comparisons. Private validation inputs, answers, arguments, and sensitive failure details do not leak through graphs, APIs, charts, or inspectors.
6. A passing exact commit and matching workflow revision become active together. One automatic rerun uses those pinned identities, answers correctly, shows its actual new tool call and trace, and returns the user to Ask while they are following the job. Opening Harness independently shows the same active diagram and complete retained history.
7. Rollback restores the previous code and graph together; historical and in-flight runs retain their original graph. Rejected proposals remain inspectable. Context/schema-only changes appear in the diff; stable IDs, shared dependencies, and deterministic layout avoid false additions or visual jumps.
8. A failing candidate, external dependency needing a contract, graph integrity mismatch, duplicate request, stale parent, infrastructure outage, refresh, or server restart never causes duplicate evaluation/promotion/rerun or a false success screen. Snapshot and promotion crash recovery cannot expose a commit paired with the wrong graph. Persisted diagrams remain viewable when tracing is unavailable. Existing inventory runs and CLI evolution continue to work.
9. Keyboard navigation, the equivalent list/table, reduced motion, narrow-screen layout, and reconnect status work without losing selection or focus. Completion does not navigate away from unrelated work.

Cover graph identity, extraction, redaction, proposal-to-candidate diffs, and matched chart aggregation with unit tests. Add browser tests for the full diagnosis → proposed tool → live comparison → saved active workflow journey, failure states, refresh/reconnect, and accessibility.
