# Phase 1 — Base analyst and Atlas-backed data

**Outcome:** a small custom agent can answer a simple question over a structured table stored in MongoDB Atlas using a model and two or three explicit tools. Its inputs and outputs are reproducible enough for later evaluation.

## Build

1. Implement the Python package and CLI entry point in `pyproject.toml` and `src/self_heal/cli.py`. Add the smallest dependencies needed for the OpenAI-compatible model API, LangSmith SDK, configuration, PyMongo, and pytest; pin them in the lockfile. The CLI accepts a natural-language question for a demo and a structured task for reproducible evaluation. Question interpretation uses the same model and shared run limits. A supported question gets a conversational answer; an ambiguous or unsupported question gets a conversational capability response and the explicit `outcome=unsupported` result for later tracing. Actual execution failures retain `outcome=error`. Structured tasks and `--json` retain the answer, outcome, and run metadata.
2. Implement `src/self_heal/model.py` as a thin OpenAI-compatible OpenRouter client for the agent and evolution calls. Keep the client interface suitable for LangSmith `wrap_openai` in Phase 3; do not add a LangChain agent framework. Keep agent model/settings stable across baseline and candidate runs. Supply a scripted model double for local component checks; a live provider call is a separate connection check.
3. Implement `src/self_heal/table_store.py` as the trusted PyMongo adapter for analyst data in Atlas. Store immutable dataset metadata and rows in `analyst_datasets` and `analyst_rows`, keyed by dataset ID and row position with a unique row index. Materialize a dataset only through the trusted runner, verify its row count and a canonical content hash that excludes MongoDB-generated IDs, and publish it for reads only when complete. Reject updates to a published dataset. Give the harness a run-scoped table-access interface that exposes schema and bounded, ordered row pages for its assigned dataset. The interface accepts no arbitrary collection name, dataset ID, or unrestricted MongoDB query; enforce page, byte, and time limits on the trusted side.
4. Implement `harness/agent.py` as a bounded model → tool → result loop with a clear stop condition and structured final answer. Implement `harness/tools.py` with schema inspection and bounded row reading through the table-access interface; `harness/context.py` assembles instructions and recent tool results. A tool implementation may iterate pages inside one model tool call, subject to fixed external limits, so Phase 4 can generate a reusable bulk mechanism without a prewritten aggregation tool or a change to the trusted data interface.
5. Add a reproducible small inventory dataset definition under `evals/analyst/data/` with fields such as `sku`, `warehouse`, `category`, `on_hand`, and `reserved`, and seed its rows into Atlas before the first task. Keep the initial working question small enough for row-by-row reading. Define a larger grouping question that stresses the initial approach under the same fixed call/context budget. The data generator and expected answers are completed in Phase 2; committed definitions are not a runtime table source.
6. Fill `config/analyst.yaml` with the supported task and output schema, allowed fields, table-page and byte limits, tool-call/step/token/time limits, and the `harness/` edit boundary. Size the fixed data-read budget to permit complete reads of supported bulk cases while the initial model-call/context budget still exposes the missing aggregation capability. Define missing-value and invalid-row behavior explicitly; do not silently invent numeric values.

## Configuration

Copy `.env.example` to `.env`. Supply `ATLAS_URI` and `ATLAS_DATABASE` to seed and read the table, plus `OPENROUTER_API_KEY` and `OPENROUTER_AGENT_MODEL` for a live smoke run. `OPENROUTER_EVOLUTION_MODEL` becomes necessary in Phase 4. The trusted runner owns the Atlas URI; the editable harness interface and model context receive no connection string or GitHub credentials. Phase 4 enforces this separation across a container boundary for generated code.

## Completion checks

- The small dataset is materialized in Atlas with the expected row count and content hash; the agent answers natural-language East and West questions by interpreting each into the supported task contract, reading through the scoped table interface, and producing the correct structured answer. Both scripted model checks and live smoke runs cover this path.
- The tool loop exposes only registered tools, obeys the configured step limit, and reports a clear failure when it cannot complete.
- An unsupported natural-language request exits normally with no table read and is distinguishable from a model-format, provider, budget, or tool failure. Phase 3 will persist and trace this outcome; Phase 1 only returns it in the run result.
- A request for another dataset or collection, an oversized page, or an unbounded query is rejected by the trusted table interface. Source and data are independent of any future generated improvement; there is no prewritten aggregation tool to select.

**Phase deliverables:** `pyproject.toml`, `harness/{agent,tools,context}.py`, `config/analyst.yaml`, `src/self_heal/{cli,model,settings,table_store}.py`, a small inventory dataset definition whose rows are materialized in Atlas, and a bulk grouping task definition under `evals/analyst/data/` for Phase 2.
